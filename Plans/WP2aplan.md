Q1 — BATCH DIMENSION: where the stack assumes batch==1
The important finding up front: almost every compute module is written batch-generic (B = x.dim(0) everywhere), so B>1 propagates cleanly through attention, MoE, RoPE and the model wrappers. The batch==1 assumptions are concentrated in (a) the KV-cache concatenation contract and (b) the engine's host-side scalar plumbing — not the math kernels.

Under the current fused SDPA + concat design, tiling is required; true broadcast sharing needs an attention rewrite.

Q2 — SPECULATION HOOK SHAPE
Where a SpeculationPolicy naturally hooks
The engine already funnels all logit production through one injected closure: DiffusionEngine.Forward = (windowIds, activeLen) -> logits [1, activeLen, V], typealias at /Users/andrebarlocher/Documents/Swift/NeoDiffusion/Packages/DiffusionGeneration/Sources/DiffusionEngine.swift:143. It is constructed in generate (lines 161-167) and generateCached (lines 230-295) and threaded down through run → denoisePhase → windowStep. Inside windowStep it is called at line 748:

let logits = forward(window, A)   // [1, A, V] FP32
This forward boundary is the exact hook point. A draft-verify cycle replaces the plain forward for the active window with a policy-mediated forward that: proposes cheap draft states, batches them (the A-column window becomes a [B, A, V] verification), and returns accepted logits. Everything downstream of line 748 (softmax, Γ/M2T selection, Δ/T2T selection, argmax, the state update nextWindow = which(finalTransfer, x0, windowActive) at line 795) is written as pure MLX array ops and would be reused verbatim on the verified logits.

How draft-verify coexists with the K-step loop-control batching (they are orthogonal)
Your instinct is correct — these are two different batching axes:

K-step speculative loop control (denoisePhase, lines 602-705): builds up to K sequential windowSteps into one graph (loop at 613-627), then does one blocking readback of the stacked [2K] break/activation flags (lines 630-643). This is about amortizing host↔GPU sync over the time/step axis. Overshoot past a break is discarded via per-step snapshots (lines 619, 683) so the result is exact and K-invariant (docstring lines 20-24, 553-561). It does not add a batch dimension to the tensors — every windowStep is still [1, A, V].
Draft-speculation (Spiffy) would add a batch dimension to a single step: within one windowStep, propose B candidate draft states and verify them in one [B, A, V] forward. This is orthogonal to K.
They compose cleanly: the natural design is to keep the K-step outer loop untouched and make the inner forward (line 748) the policy-mediated proposer/verifier. Each of the K speculative steps calls policy.forwardAndVerify(window, A) which internally runs the batched draft-verify and returns a single accepted [1, A, V] logits (or an accepted multi-position update) that the existing Γ/Δ machinery consumes. Because the K-loop already tolerates discarding overshoot, a draft-rejection that shortens progress is naturally absorbed. The cleanest seam is: introduce a SpeculationPolicy protocol whose single method wraps Forward, inject it alongside speculationK in DiffusionEngine.init (lines 45-50), and call it at DiffusionEngine.swift:748. The K-batching (breakFlags at line 608, etc.) stays exactly as is.

Causal / AR mode (block size 1) support — for the S2D2 verifier
BlockDiffusionMask.build with blockLength=1 produces a token-level causal mask — verified by the math. At line 43: blockIndex = MLXArray(0..<L).floorDivide(1) → blockIndex[p] = p. Then line 44: allowed = blockIndex[i] >= blockIndex[j] becomes i >= j, i.e. the standard lower-triangular causal mask; .strict fills 0/-inf (line 48). The comment at lines 41-43 explicitly warns that integer floor-division is what keeps it block-causal — with blockLength=1 that reduces exactly to per-token causality. So an AR/causal verifier mask is already expressible with no new code, and the .referenceBias variant would give the +1/0 form (line 50) if ever needed.
activeWindowMask at blockLength=1 (lines 65-77): activePart = build(totalLength: activeLen, blockLength: 1) → causal over the active window; prefix columns all-zero (allowed). This yields exactly the S2D2 "prefix-allowed + causal-active" verifier mask.
Engine support for blockLength=1 runs: blockLength is a free GenerationParams field (/Users/andrebarlocher/Documents/Swift/NeoDiffusion/Packages/DiffusionGeneration/Sources/GenerationParams.swift:29, blockLength: Int = 32). The engine requires only totalLength % blockLength == 0 (BlockDiffusionMask.build precondition line 40) and numBlocks = (promptLength + genLength + B - 1)/B (DiffusionEngine.swift:370). With B=1, genLength and padding trivially satisfy the multiple-of-B constraint. Caveats: (1) denoisePhase asserts numToTransfer == 1 (line 585) — fine for AR. (2) The MoE/attention would run one active token at a time against the cached prefix (activeIds [1,1]), which is precisely an AR decode step — the cached forward path (generateCached, lines 230-253) already supports arbitrary activeLen including 1 (single-block, mask nil fast path at line 243). (3) With B=1 the whole slot scheduler still runs but each "block" is one token; τadd/τsemi machinery is inert at nBuf=1 (defaults tauAdd=2.0 = never activate, GenerationParams.swift:45/75). So an S2D2 block-size-1 AR verifier pass is directly reachable: run the cached forward over a 1-token active window under a blockLength=1 causal mask. No structural blocker; the main work is exposing it as a distinct verify entry point rather than the diffusion loop.
